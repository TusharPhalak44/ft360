## 2. Planned Test Case Specification (Unit, Integration, Negative Security & E2E)

### 2.1 Unit Tests (`apps/api/test/unit/phase3-auth-and-guards.spec.ts`)
- **UT-P3-01:** `PasswordHashService` produces Argon2id hashes (`$argon2id$v=19$m=65536,t=3,p=4$...`), verifies valid passwords, rejects wrong passwords, and executes constant-time dummy verification on `null` candidate hash.
- **UT-P3-02:** Password policy validator rejects `<12` chars, `>128` chars, missing character classes, and email-matching passwords.
- **UT-P3-03:** `TokenService` signs and verifies Access JWT claims (`sub`, `sid`, `tid`, `mid`, `padmin`), rejects expired/tampered/wrong-issuer tokens, and hashes opaque refresh/reset/verify tokens deterministically with SHA-256.
- **UT-P3-04:** `CsrfProtectionGuard` allows safe `GET`/`HEAD`/`OPTIONS`, enforces `Origin` + `X-CSRF-Token` on cookie-authenticated `POST`/`PUT`/`PATCH`/`DELETE`, and rejects mismatched/missing CSRF tokens with `403 CSRF_TOKEN_INVALID`.
- **UT-P3-05:** `JwtAuthGuard`, `PlatformSuperAdminGuard`, and `TenantAdminGuard` reject missing/revoked sessions, enforce plane separation (`tid === null` for platform routes; non-null verified `tid` for workspace routes), and block unauthorized roles.
- **UT-P3-06:** `AuthAuditService` redacts/rejects any accidental `password`, `token`, or `hash` fields in `metadata`.

### 2.2 Database & HTTP Integration Tests (`apps/api/test/integration/phase3-auth-workflows.int-spec.ts`)
- **IT-P3-01 (Clean Migration & Rollback):** Roll back `0005 -> 0004`, re-apply `0005`, verify SHA-256 checksums, `FORCE RLS` on all 13 domain tables, and `0` `SELECT (password_hash)` grant on `public.users`.
- **IT-P3-02 (Registration & Email Verification):** Register user (`PENDING`, `email_verified=false`) → login before verification rejected (`403 EMAIL_NOT_VERIFIED`) → verify email with single-use token (`ACTIVE`, `email_verified=true`) → replay of consumed verification token rejected (`400`).
- **IT-P3-03 (Login, Cookies, `/auth/me`, & Logout):** Login sets `HttpOnly` `ft360_at` & `ft360_rt` + `ft360_csrf`; `/auth/me` returns profile with **zero** `passwordHash`/`refreshTokenHash` fields; `/auth/logout` revokes session in PG + Redis so subsequent request with the same `ft360_at` JWT is immediately rejected (`401 SESSION_REVOKED`) even before JWT `exp`.
- **IT-P3-04 (Refresh Rotation & Session Expiration):** `/auth/refresh` issues new `ft360_at` + `ft360_rt` and invalidates prior refresh token; expired `idle_expires_at` / `expires_at` sessions are rejected (`401 SESSION_EXPIRED`).
- **IT-P3-05 (Forgot & Reset Password):** `/auth/forgot-password` returns identical `202` for known and unknown emails; `/auth/reset-password` updates Argon2id hash, rejects old password, accepts new password, and immediately revokes all pre-existing active sessions for that user.
- **IT-P3-06 (Multi-Tenant Org Selection & Switching):** Shared user belonging to Tenant A (`tenant_admin`) and Tenant B (`sales_rep`) logs in (`tid=null`) → selects Tenant A → `/workspace/context` returns Tenant A & `/workspace/admin/auth-logs` returns `200` → switches to Tenant B → `/workspace/context` returns Tenant B & `/workspace/admin/auth-logs` returns `403 INSUFFICIENT_TENANT_PERMISSIONS`.

### 2.3 Mandatory Negative Security Tests (`apps/api/test/integration/phase3-auth-negative-security.int-spec.ts`)
- **SEC-P3-01 (Refresh Token Replay / Theft Detection):** Replaying an already-rotated `ft360_rt` immediately revokes the **entire `family_id` session lineage** (both attacker and victim rotated token invalidated -> `401 REFRESH_TOKEN_REPLAY_DETECTED`) and logs `AUTH_REFRESH_REPLAY_DETECTED`.
- **SEC-P3-02 (Frontend Tenant Spoofing Rejected):** Sending `x-tenant-id`, `?tenant_id=`, or `{ tenantId }` to login or workspace endpoints fails with `400 UNTRUSTED_TENANT_INPUT_REJECTED`; calling `/auth/select-organization` with a `targetOrganizationId` the user does not belong to (or where membership/tenant is `SUSPENDED` or `INVITED`) fails with `403` and leaves `active_tenant_id = NULL`.
- **SEC-P3-03 (Mid-Session Suspension Kill-Switch):** Suspending a user, revoking their `tenant_memberships` row, or suspending their `tenants` row blocks their very next API call (`401`/`403`) even while their 15-minute Access JWT is still cryptographically unexpired.
- **SEC-P3-04 (Platform Super Admin vs Tenant Admin Boundary Isolation):**
  - Tenant Admin calling `/api/v1/platform/*` -> `403 PLATFORM_SUPER_ADMIN_REQUIRED` + `DENIED` audit log.
  - Platform Super Admin (without membership in Tenant A) calling `/api/v1/workspace/*` or `/auth/select-organization` for Tenant A -> `403 TENANT_MEMBERSHIP_DENIED`.
- **SEC-P3-05 (CSRF Enforcement on Cookie Auth):** Mutating cookie-authenticated `POST /auth/select-organization`, `POST /auth/refresh`, and `POST /auth/logout` without `X-CSRF-Token` (or with cross-site `Origin: https://evil.example`) fail with `403 CSRF_TOKEN_INVALID`.
- **SEC-P3-06 (Login Brute-Force Rate Limiting):** `5` consecutive failed logins trigger `429 AUTH_RATE_LIMITED` with `Retry-After` header and `AUTH_LOGIN_LOCKED` audit record — even if the 6th attempt supplies the **correct** password during lockout.
- **SEC-P3-07 (Audit Log Immutability & Cross-Tenant RLS):** `ft360_app` `UPDATE` or `DELETE` on `public.auth_audit_logs` fails with `42501`; Tenant A Admin querying `/workspace/admin/auth-logs` sees `0` events from Tenant B or global other-user logins.
- **SEC-P3-08 (Zero Secret Exposure & Narrow `SECURITY DEFINER` Guard):** Calling `fn_auth_get_login_candidate` from inside a tenant transaction returns `0` rows; inspecting all Phase 3 JSON responses and `Set-Cookie` headers confirms `password_hash`, `refresh_token_hash`, and `csrf_secret_hash` never appear in any API response.
