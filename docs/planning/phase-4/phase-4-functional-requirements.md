## 1. Guiding Domain Invariants

1. **Global Users, Tenant-Scoped Memberships:** Every human user has at most **one** global identity row in `public.users` (keyed by case-insensitive `CITEXT` `email`). Belonging to `N` organizations creates `N` isolated rows in `public.tenant_memberships` — never duplicate `users` rows.
2. **Strict Plane Separation:** Platform Super Admins (`users.is_platform_super_admin = TRUE`) operate exclusively in the **Platform Control Plane** (`activeTenantId = NULL`, guarded by `PlatformSuperAdminGuard`). Tenant Administrators operate exclusively inside a single **Verified Tenant Plane** (`TenantMembershipGuard` + `TenantAdminGuard` / `TenantPermissionGuard`). Platform Super Admins are never members of customer tenants, and Tenant Admins never acquire `PLATFORM`-plane permissions.
3. **Never Trust Client Tenant Identifiers:** Every tenant-plane operation (`#3`–`#25`, `#29`) derives `tenantId` and `membershipId` exclusively from server-validated `auth_sessions` (`req.tenantContext`). Only explicit control-plane routes (`/api/v1/platform/tenants/:tenantId/*`) or org-selection (`/api/v1/auth/select-organization`) opt in via `@AllowExplicitTenantTarget()`.
4. **Atomic Provisioning:** A tenant organization never exists in a half-initialized state without seeded system roles (`tenant_admin`, `member`), `1:1` companion records (`tenant_profiles`, `tenant_settings`, `tenant_branding_settings`, `tenant_onboarding_states`), and either an active `is_primary_owner = TRUE` `tenant_admin` (self-registration / existing-user platform provisioning) or a pending initial admin invitation (new-user platform provisioning).

### Module 4.4 — Tenant Lifecycle Management & Suspension Enforcement

#### 4.4.A Complete State-Transition Matrix

`CANCELLED` is the **sole terminal state** (zero outbound transitions permitted in application or SQL). Every transition requires **`PlatformSuperAdminGuard` (`platform:tenants:manage`)** and a mandatory **`reason` (`10–500` trimmed characters)**. Any unlisted transition (including self-transitions `X -> X`, `ACTIVE -> TRIAL`, `* -> PROVISIONING`, `DEACTIVATED -> TRIAL`, **`TRIAL -> CANCELLED` / `ACTIVE -> CANCELLED`**, and `CANCELLED -> *`) is rejected with `409 INVALID_TENANT_STATUS_TRANSITION`. **Confirmed Cancellation Rule (`OD-P1`):** Operational tenants (`TRIAL` or `ACTIVE`) **must first transition to `SUSPENDED` or `DEACTIVATED`** before terminal `CANCELLED` is permitted (`PROVISIONING` may cancel directly before customer onboarding begins).

| *(Creation)* | Platform Provision | `PROVISIONING` / `TRIAL` / `ACTIVE` | Platform Super Admin (`platform:tenants:manage`) | **Yes (`10–500` chars)** | Sets `activated_at = NOW()` if `ACTIVE` |
| `PROVISIONING` | `ACTIVATE` (`TRIAL`) | `TRIAL` | Platform Super Admin (`platform:tenants:manage`) | **Yes** | Unlocks workspace entry for initial admin |

#### 4.4.C 4-Layer PostgreSQL Lifecycle Validation When Redis Is Unavailable & Measurable Latency

1. **Layer 1 — Fail-Safe `RedisSessionCacheService` & Cache Degradation (Never Fail Open, Never Block Control Plane):**
   - All `RedisSessionCacheService` methods (`isSessionTombstoned`, `getCachedSession`, `cacheActiveSession`, `tombstoneSessions`, `evictSessionCache`, `markAllUserSessionsRevoked`) and tenant settings/branding cache helpers wrap `ioredis` calls in bounded `try/catch` blocks (`REDIS_UNAVAILABLE_FALLBACK_PG` structured warning with `correlationId`).
   - Because `JwtAuthGuard` **unconditionally** executes `authRepo.validateSessionInDb` (`fn_auth_validate_session`) on every request, Redis errors degrade directly to PostgreSQL without ever granting cached access—and Platform Super Admins can still execute `#33 POST /api/v1/platform/tenants/:tenantId/lifecycle` during a total Redis outage.
2. **Layer 2 — Atomic PostgreSQL Transition & Session Validation (`T = 0ms` at `COMMIT`):**
   - `fn_platform_transition_tenant_status` locks `public.tenants` `FOR UPDATE`, validates the 6-state matrix + `OD-P1` inside PostgreSQL, updates `tenants.status`, and clears `active_tenant_id = NULL, active_membership_id = NULL` on all non-revoked `public.auth_sessions` rows for that tenant in **one ACID transaction** (returning `evicted_session_ids UUID[]` for best-effort post-commit Redis deletion).
   - `fn_auth_validate_session` (`LEFT JOIN public.tenants t ON t.id = s.active_tenant_id`) validates in PostgreSQL that any bound `active_tenant_id` has `t.status IN ('ACTIVE', 'TRIAL')` (returning unbound/non-operational status otherwise).
3. **Layer 3 — Pre-Controller PostgreSQL Guard (`TenantMembershipGuard` -> `fn_verify_tenant_membership`):**
   - Every `/api/v1/workspace/*` request executes `fn_verify_tenant_membership(user_id, tenant_id)` (`INNER JOIN public.tenants t ON t.id = tm.tenant_id`, `0` Redis calls), rejecting `PROVISIONING`, `SUSPENDED`, `DEACTIVATED`, and `CANCELLED` directly from PostgreSQL (`403 TENANT_SUSPENDED_OR_INACTIVE`).
4. **Layer 4 — In-Transaction PostgreSQL Gate (`withVerifiedMemberTransaction` + `fn_assert_tenant_operational` + Write RLS):**
   - `TenantTransactionManager.withVerifiedMemberTransaction` re-verifies `tenant_status IN ('ACTIVE', 'TRIAL')` inside `BEGIN ... COMMIT` before domain SQL runs.
   - Every invitation, preview, acceptance, outbox-claim, and worker routine invokes `public.fn_assert_tenant_operational(v_tenant_id)` (`SELECT status FROM public.tenants WHERE id = p_tenant_id FOR SHARE` -> `42501` if not `ACTIVE`/`TRIAL`), and Phase 4 tenant `INSERT`/`UPDATE`/`DELETE` RLS policies require `public.fn_is_current_tenant_operational()` (`EXISTS (SELECT 1 FROM public.tenants t WHERE t.id = app_current_tenant_id() AND t.status IN ('ACTIVE', 'TRIAL'))`), guaranteeing PostgreSQL itself blocks mutations on suspended/inactive tenants even if Redis is completely unreachable.
5. **Measurable Enforcement Latency:** **`0ms` logical window post-commit**, with automated integration assertions requiring **`< 200ms` HTTP denial latency (`< 1,000ms` worst-case SLA)** both when Redis is healthy and when Redis is completely offline.

### Module 4.6 — User Invitations, Initiator/Recipient Identity Separation & Atomic Dual-Path Acceptance

| Req ID | Requirement Specification |
|---|---|
| **FR-4.6.1 (Issue, Resend & Revoke)** | • `POST /api/v1/workspace/invitations` (`tenant:invitations:manage`, plus `tenant:admins:manage` if `targetRoleId` is `tenant_admin`) creates a `PENDING` invitation (`32`-byte CSPRNG raw token -> `CHAR(64)` SHA-256 `token_hash`, TTL defaulted to `168h` and configurable `1–720h` per confirmed `D3`), seals the raw token via HKDF `AES-256-GCM` into `auth_email_outbox` (`kind = 'TENANT_INVITATION'`), and enqueues BullMQ delivery.<br>• `POST .../resend` enforces `60s` cooldown and `resend_count < 10`, rotates `token_hash` (immediately invalidating prior emailed links), supersedes prior unsent outbox rows for that `invitation_id`, and extends `expires_at`.<br>• `POST .../revoke` transitions `PENDING -> REVOKED`, expires unsent outbox rows (wiping ciphertext), and blocks acceptance. |
| **FR-4.6.2 (Strict Separation Between Initiating User & Invitation Recipient Identity)** | 1. **Initiator (`Inviter`) Identity:** `invited_by_user_id` and `invited_by_membership_id` on `tenant_invitations` (plus `initiated_by_user_id` on `auth_email_outbox`) are populated exclusively from server-verified GUC `app_current_user_id()` and `req.tenantContext.membershipId`—never from client payloads. Self-invitation (`lower(btrim(inviter.email)) = lower(btrim(invited_email))`) is rejected (`422 CANNOT_INVITE_SELF`).<br>2. **Recipient (`Invitee`) Identity Pre-Acceptance:** While `status = 'PENDING'`, the recipient is represented solely by canonical `invited_email` (`chk_ti_pending_recipient_unbound` enforces `accepted_by_user_id IS NULL AND accepted_membership_id IS NULL`). In `auth_email_outbox`, `chk_auth_email_outbox_anchor` enforces **`user_id IS NULL`** for `kind = 'TENANT_INVITATION'`, preventing the initiating admin's `user_id` from ever being stored in the recipient `user_id` column.<br>3. **Recipient Identity at Acceptance & Initiator Collision Block:** `chk_ti_initiator_recipient_distinct` enforces `accepted_by_user_id <> invited_by_user_id`. If the initiating admin (or any other signed-in user) opens the invitation link while authenticated under their own session, `#27 POST /invitations/accept` rejects with `403 INVITATION_EMAIL_MISMATCH` without consuming the token or mutating the initiator's membership, and `RV-12` (`/invitations/accept`) prompts `Sign Out to Continue as Invited Recipient`. Audit trails attribute `TENANT_INVITATION_CREATED`/`RESENT`/`REVOKED` to `actor_user_id = inviter` and `TENANT_INVITATION_ACCEPTED` to `actor_user_id = recipient` (`metadata.invitedByUserId = inviter`). |
| **FR-4.6.3 (Replay, Expiration & Concurrency Guarantees)** | Both acceptance routines execute `SELECT * FROM public.tenant_invitations WHERE token_hash = p_token_hash FOR UPDATE` at transaction start:<br>1. **Single-Use Replay Defense:** Concurrent requests on the same token serialize on `FOR UPDATE`; the winner sets `status = 'ACCEPTED'`, and all subsequent/concurrent attempts see `status <> 'PENDING'` and fail (`400 INVITATION_INVALID_OR_EXPIRED` / `409`).<br>2. **Expiration Enforcement:** Checks `expires_at > NOW()` against PostgreSQL transaction clock; expired `PENDING` rows fail closed (`400 INVITATION_INVALID_OR_EXPIRED`).<br>3. **Tenant Operational Gate:** Calls `fn_assert_tenant_operational(v_inv.tenant_id)` (`SELECT status FROM public.tenants FOR SHARE` requiring `ACTIVE` or `TRIAL`, `403 TENANT_SUSPENDED_OR_INACTIVE` otherwise, without burning the token). |
| **FR-4.6.4 (Path A — Existing Global User Acceptance `POST /invitations/accept`)** | Executes inside `withAuthenticatedUserTransaction` -> `fn_invitation_accept_existing_user`:<br>1. Locks caller's `public.users` row `FOR SHARE`; requires `status = 'ACTIVE'`, `email_verified = TRUE` (`403 EMAIL_NOT_VERIFIED` otherwise), `is_platform_super_admin = FALSE` (`403`), and `users.id <> v_inv.invited_by_user_id`.<br>2. **Verified Recipient Email Match:** Enforces `lower(btrim(users.email::text)) = lower(btrim(invitation.invited_email::text))`; mismatches fail with `403 INVITATION_EMAIL_MISMATCH` without consuming the token.<br>3. Inserts `ACTIVE` `tenant_memberships` (`uq_tenant_memberships_tenant_user`, or reactivates a previously `REVOKED` row for `(tenant_id, user_id)`), inserts `user_role_assignments`, marks invitation `ACCEPTED` (`accepted_by_user_id = caller.id`), binds `auth_sessions` to `(tenant_id, membership_id)`, and writes atomic `tenant_audit_logs` + `auth_audit_logs` entries. |
| **FR-4.6.5 (Path B — New Global User Creation & Duplicate-Email Concurrency `POST /invitations/accept-register`)** | Executes Argon2id hashing (`PasswordHashService`) followed by single atomic transaction `fn_invitation_accept_new_user`:<br>1. Locks `tenant_invitations` `FOR UPDATE` (`PENDING`, `expires_at > NOW()`, operational tenant via `fn_assert_tenant_operational`).<br>2. **Database Unique Constraints & Concurrent Registration Serialization:** Acquires `pg_advisory_xact_lock(hashtext('global_user_email:' || lower(btrim(v_inv.invited_email::text))))` (shared with `fn_auth_register_user`) and checks `public.users`. At the schema layer, `CONSTRAINT uq_users_email UNIQUE (email)` (`CITEXT`), `chk_users_email_canonical_trimmed`, and functional unique index `uq_users_email_normalized ON public.users (lower(btrim(email::text)))` guarantee **zero duplicate global email rows** even under parallel cross-tenant `accept-register` or `/auth/register` races (`SQLSTATE 23505` `unique_violation`). Any existing or concurrently committed email aborts cleanly with `409 USER_ALREADY_REGISTERED_SIGN_IN_TO_ACCEPT` **without consuming the losing transaction's `PENDING` invitation token**.<br>3. Inserts `1` global `public.users` row (`email = lower(btrim(v_inv.invited_email::text))::citext`, `status = 'ACTIVE'`, `email_verified = TRUE`, `is_platform_super_admin = FALSE`), creates `ACTIVE` `tenant_memberships` + `user_role_assignments`, marks invitation `ACCEPTED`, creates generation-1 `auth_sessions` + `auth_refresh_token_history` bound to the tenant, and writes atomic `auth_audit_logs` + `tenant_audit_logs` entries. |
